# agent-role

> Status: Draft  
> Scope: project-specific term for HyperGraph methodology  
> Related: `docs/terms/project/terms_map.md`

## 1. Назначение термина

`agent-role` — это role entity внутри methodology проекта.

Она нужна, чтобы формализовать самодостаточный reusable профиль исполнителя для AI-first разработки: каков его образ мышления, какие ограничения на него распространяются и какими capabilities он обладает.

В Kilo Code частным случаем `agent-role` является `mode`, но в методологии проекта понятие роли шире, чем конкретный runtime mode.

Важно:
- `agent-role` не указывает конкретную `LLM model`, которая будет использоваться агентом;
- модели могут меняться, а role profile должен оставаться стабильным и переносимым;
- одна и та же роль может входить в reusable набор ролей и затем использоваться в разных проектах.

## 2. Что описывает `agent-role`

Каждая `agent-role` должна задавать как минимум:
- `system_prompt`;
- подмножество `rules`, которое применяется к роли;
- подмножество `skills`, которое доступно роли;
- подмножество `MCP tools`, которое доступно или предпочтительно для роли;
- optional `when_to_use` как краткую guidance-подсказку, для чего роль в целом полезна.

То есть `agent-role` описывает не шаг workflow, а reusable профиль специалиста.

## 3. Аналогия для понимания

Полезная аналогия такая:
- `agent-role` — это специалист определенного образа мышления с `system_prompt`, набором навыков `skills` и доступных инструментов `MCP tools`;
- назначение на конкретный шаг workflow — это уже отдельная `step-vacancy` внутри процесса, которая выбирает подходящую роль под задачу шага.

Один и тот же специалист может закрывать похожие позиции в разных workflow и разных проектах.

## 4. Роль внутри methodology

В этой проектной методологии разработка ПО рассматривается как работа команды ИИ-агентов и человека по согласованному `methodology workflow`.

При этом `agent-role` не знает, на каких именно шагах workflow ее будут использовать. Роль остается переносимой и самодостаточной сущностью.

Поэтому `agent-role` — это не описание шага, а описание исполнителя:
- с каким `system_prompt` он работает;
- какие `rules` на него распространяются;
- какие `skills` ему доступны;
- какие `MCP tools` он может использовать.

## 5. Связь с `methodology workflow`

`methodology workflow` определяет центральную последовательность шагов разработки.

Именно workflow решает:
- на каком шаге появляется конкретная `step-vacancy`;
- какая `agent-role` подходит для этой `step-vacancy`;
- когда одна и та же роль переиспользуется в разных шагах;
- как роли комбинируются между собой в рамках процесса.

Связь здесь однонаправленная:
- `workflow` определяет `step-vacancy`;
- `step-vacancy` ссылается на `agent-role`;
- `agent-role` не содержит знания о конкретных шагах workflow.

Именно поэтому `agent-role` является first-class понятием в методологии проекта, но не подменяет собой модель workflow.

## 6. Переносимость и переиспользование

`agent-role` потенциально является переносимой и самодостаточной сущностью.

Это значит, что role definition может:
- лежать в общем reusable наборе ролей или внутри role pack;
- подключаться как подмножество в конкретную methodology проекта;
- использоваться в разных workflow;
- использоваться в разных проектах без жесткой привязки к одному process layout.

Именно workflow и methodology решают, где и когда применять роль, а не наоборот.

## 7. Почему это важно для агента и человека

Явное описание `agent-role` нужно, чтобы:
- человеку было понятно, какого специалиста он подключает в workflow;
- агент мог понимать свои рабочие границы без догадок;
- одну и ту же роль можно было переиспользовать в разных workflow;
- одну и ту же роль можно было переиспользовать в разных шагах одного workflow;
- methodology можно было навигировать и materialize как согласованный runtime layer;
- разные agent environments можно было поддерживать через один и тот же концепт роли.

## 8. Что не стоит смешивать с `agent-role`

С `agent-role` не стоит смешивать:
- конкретную `LLM model`;
- конкретную позицию на шаге workflow;
- описание входов и выходов шага;
- единичный `workflow`;
- отдельный `skill`;
- конкретный tool call.

`agent-role` — это self-contained role profile, которое задает системное поведение и operational capabilities, но не описывает position внутри конкретного workflow.

## 9. Минимальные поля для будущей спецификации

На уровне будущей спецификации для `agent-role` стоит ожидать как минимум:
- `role_id`;
- `name`;
- optional `slug`;
- `description`;
- `system_prompt`;
- optional `when_to_use`;
- `allowed_skills`;
- `allowed_rules`;
- `allowed_mcp_tools`;
- optional `file_access_policy`.

## 10. Связанные термины

`agent-role` нужно читать вместе с:
- `methodology`;
- `methodology workflow`;
- `workflow`;
- `step-vacancy`;
- `role-specific rules`;
- `role-specific skills`;
- `role-specific MCP tools`.

Этот термин является одним из ключевых project-specific понятий для documentation package слоя `Project Methodology Runtime`.
