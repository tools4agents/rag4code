# workflow

> Status: Draft  
> Scope: project-specific term for HyperGraph methodology  
> Related: `docs/terms/project/terms_map.md`

## 1. Назначение термина

`workflow` — это markdown-артефакт, который описывает полезную последовательность шагов для достижения некоторого результата.

Он нужен, чтобы зафиксировать:
- для чего нужен процесс;
- какие шаги в него входят;
- как человек и агент могут пройти по этому процессу от начала до результата.

`workflow` может быть:
- частью общей методологии проекта;
- локальным процессом для отдельной задачи;
- reusable process pattern, который можно применять повторно.

## 2. Что описывает `workflow`

На уровне проекта `workflow` описывает:
- цель workflow и зачем он нужен;
- optional входы workflow, если они нужны до старта;
- последовательность шагов с кратким идейным описанием;
- optional выход workflow.

Минимально workflow должен описывать:
- для чего он нужен;
- последовательность шагов.

## 3. Связь с `workflow-step`

`workflow` — это карта процесса.

Каждый шаг в этой карте должен ссылаться на отдельный markdown-документ `workflow-step`, который раскрывает этот шаг подробно.

То есть:
- `workflow` дает обзорную навигацию по процессу;
- `workflow-step` дает глубокое описание конкретного шага.

Такой подход поддерживает `lazy loading` и `progressive disclosure`.

## 4. Связь с `methodology workflow`

`methodology workflow` — это частный, центральный для проекта workflow.

Он отличается тем, что:
- задает основную методологий разработки (например, waterfall, Scrum, kanban, исследовательский PoC, соревнование с сильным Deep research и быстрой проверкой гипотез, любая другая которую придумают пользователи проекта и их ИИ агенты);
- является главным процессом по которого придерживаются пр разработке даного проекта;
Мы стремимся, чтобы разработчикам и агентам было удобно работать над проектом. Методология носит рекомедательный характер, и насколько ее придерживаться разработчики решают сами. Все для удобства разработчиков и агентов.
- определяет, как связываются роли, шаги и результаты разработки.

При этом не каждый `workflow` обязан быть `methodology workflow`.

В проекте могут существовать и другие workflow:
- document consolidation workflow;
- architect review workflow;
- task handoff workflow;
- исследовательский workflow.

## 5. Связь с `step-vacancy` и `agent-role`

На уровне самого `workflow` обычно не нужно подробно раскрывать reusable semantics роли.

`workflow` должен:
- перечислить шаги;
- показать их порядок;
- при необходимости указывать, что шаг имеет связанную `step-vacancy`.

Детали того:
- какая роль нужна шагу;
- что делает шаг;
- какие у него входы и выходы;
- какие критерии завершения и провала,

уже должны подробно раскрываться в `workflow-step`.

## 6. Почему это важно

Явное введение `workflow` как отдельного термина нужно, чтобы:
- не превращать шаги в перегруженные монолиты без карты процесса;
- отделить обзор процесса от подробностей каждого шага;
- сделать документацию процесса удобной и для человека, и для агента;
- поддерживать переиспользуемые process patterns в проекте.

## 7. Что не стоит смешивать с `workflow`

С `workflow` не стоит смешивать:
- reusable semantics `agent-role`;
- подробное описание одного конкретного шага;
- runtime projection роли;
- storage layout adapter artifacts.

`workflow` — это описание процесса, а не описание специалиста или runtime representation.

## 8. Связанные термины

`workflow` нужно читать вместе с:
- `methodology workflow`;
- `workflow-step`;
- `step-vacancy`;
- `agent-role`.

Этот термин является ключевым для понимания process layer в `Project Methodology Runtime`.
