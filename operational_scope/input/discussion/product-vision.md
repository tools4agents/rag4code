# Product Vision: project-graph

## 1. Краткое видение

`project-graph` — локальный MCP-инструмент для ИИ-агентов, который строит и поддерживает граф связей между Markdown-документами внутри выбранной корневой папки проекта.

Цель проекта — перенести рутинный контроль ссылочной связности Markdown-документации с ИИ-агента и человека на быстрый детерминированный сервис: сервис знает входящие и исходящие ссылки для каждого Markdown-файла и умеет безопасно обновлять ссылки при перемещении, переименовании или удалении документов.

По пользовательскому опыту ориентиром является поведение Obsidian: если документ переименован или перемещен, ссылки на него в других документах должны быть автоматически пересчитаны.

## 2. Problem Frame

Во многих проектах документация хранится как набор Markdown-файлов, которые ссылаются друг на друга относительными путями. Примеры таких документов и областей:

- продуктовые и инициативные документы, например `hyper-eval-kit/operational_scope/initiatives/product-vision`;
- методологические слои и термины, например `hyper-graph/docs/methodology-layer/assets/terms-management`;
- архитектурные решения, спецификации, планы, glossary, operational docs и другие project-local context layers.

Текущая проблема:

- из Markdown-файла легко увидеть исходящие ссылки — на какие документы он ссылается;
- трудно быстро увидеть входящие ссылки — кто ссылается на текущий документ;
- при переименовании или перемещении файла ИИ-агент вынужден искать все упоминания через `grep`, регулярные выражения или ручной анализ;
- агент должен вручную вычислять новые относительные пути из каждого ссылающегося файла;
- это создает рутинную нагрузку, повышает риск битых ссылок и отвлекает агента от смысловой работы.

## 3. Целевые пользователи

### Основной пользователь

ИИ-агент, работающий в локальном проекте с Markdown-документацией и выполняющий операции над файлами документации.

### Вторичные пользователи

- разработчик или архитектор, который поддерживает связанную проектную документацию;
- команда, использующая Markdown как Source of Truth для продуктового, архитектурного или операционного знания;
- maintainers проектов с большим количеством cross-links между документами.

## 4. Продуктовая ценность

`project-graph` должен дать агенту не просто поиск по тексту, а структурное знание о документационной graph topology:

- какие документы связаны между собой;
- кто зависит от конкретного документа;
- какие ссылки нужно обновить при изменении пути документа;
- какие документы станут затронутыми при удалении документа;
- где есть потенциальные битые ссылки.

Ключевая ценность: уменьшить количество механической работы и ошибок при поддержке Markdown-документации, сохранив внимание ИИ-агента для продуктового, архитектурного и исследовательского reasoning.

## 5. Scope первого продукта

### In scope

1. Настройка корневой папки проекта.
   - Пользователь указывает сервису локальную папку проекта.
   - Эта папка считается project root.
   - Все пути и ссылки нормализуются относительно этого root.

2. Индексация Markdown-файлов.
   - Сервис обходит project root.
   - Находит Markdown-файлы.
   - Извлекает ссылки из Markdown-документов.
   - Строит граф, где вершина — Markdown-файл, а ребро — ссылка из одного Markdown-файла в другой.

3. Хранение графа связей.
   - Для каждого Markdown-файла доступны исходящие ссылки.
   - Для каждого Markdown-файла доступны входящие ссылки.
   - Граф может храниться в graph DB или другом backend, если он обеспечивает нужные запросы и обновления.

4. MCP-инструменты для ИИ-агента.
   - Получить список файлов, на которые ссылается Markdown-файл.
   - Получить список файлов, которые ссылаются на Markdown-файл.
   - Переместить или переименовать Markdown-файл с автоматическим обновлением ссылок на него.
   - Удалить Markdown-файл и обработать упоминания о нем в документах, которые на него ссылались.

5. Пересчет относительных ссылок.
   - При `move` сервис обновляет ссылки во всех ссылающихся Markdown-файлах.
   - Новые ссылки должны быть корректными относительно расположения каждого ссылающегося файла.

### Out of scope для первого этапа

- Полноценный UI наподобие Obsidian.
- Поддержка всех Obsidian-specific wiki-link возможностей без отдельного решения.
- Семантический анализ содержания документов.
- Автоматическое изменение не-Markdown форматов.
- Распределенная синхронизация между машинами.
- Совместное редактирование несколькими пользователями.

## 6. Предварительные MCP capabilities

### `get_outgoing_links`

Назначение: показать документы, на которые ссылается выбранный Markdown-файл.

Вход:

- путь к Markdown-файлу относительно project root или абсолютный путь внутри project root.

Выход:

- список resolved target files;
- исходный текст ссылки;
- позиция ссылки в исходном файле;
- статус ссылки: resolved, unresolved, external, unsupported.

### `get_incoming_links`

Назначение: показать документы, которые ссылаются на выбранный Markdown-файл.

Вход:

- путь к Markdown-файлу относительно project root или абсолютный путь внутри project root.

Выход:

- список source files;
- исходный текст ссылки в каждом source file;
- позиция ссылки;
- тип ссылки и статус resolution.

### `move_markdown_file`

Назначение: переименовать или переместить Markdown-файл и автоматически обновить все ссылки на него.

Вход:

- текущий путь файла;
- новый путь файла;
- режим обработки конфликтов, если целевой файл уже существует;
- опционально dry-run режим.

Выход:

- список измененных файлов;
- список обновленных ссылок;
- список ссылок, которые не удалось безопасно обновить;
- итоговый статус операции.

Ключевое поведение:

- файл физически перемещается в новое место;
- все incoming links пересчитываются относительно расположения каждого source file;
- граф обновляется после операции;
- в dry-run режиме сервис показывает planned changes без записи на диск.

### `remove_markdown_file`

Назначение: удалить Markdown-файл и обработать все ссылки на него.

Вход:

- путь к удаляемому файлу;
- стратегия обработки ссылок;
- опционально dry-run режим.

Возможные стратегии:

- удалить только файл и вернуть список broken incoming links;
- удалить ссылки на файл из source documents;
- заменить ссылки plain text упоминанием;
- пометить ссылки как удаленные через выбранный marker.

Выход:

- список затронутых файлов;
- список удаленных или измененных ссылок;
- список оставшихся broken references;
- итоговый статус операции.

## 7. Предварительная модель домена

### MarkdownFile

Markdown-документ внутри project root.

Ключевые поля:

- `path` — нормализованный путь относительно project root;
- `absolute_path` — абсолютный путь на локальной файловой системе;
- `content_hash` — хэш содержимого для определения изменений;
- `last_indexed_at` — время последней индексации;
- `status` — active, missing, deleted, ignored.

### Link

Ссылка из одного Markdown-файла в другой ресурс.

Ключевые поля:

- `source_path` — файл, где находится ссылка;
- `target_raw` — исходная строка ссылки;
- `target_resolved_path` — resolved Markdown target внутри project root, если resolution успешен;
- `link_kind` — markdown_inline, markdown_reference, autolink, wiki_link, image, external, anchor;
- `range` — позиция ссылки в source file;
- `resolution_status` — resolved, unresolved, external, ignored, unsupported.

### Graph Edge

Направленное ребро `source MarkdownFile -> target MarkdownFile`, созданное resolved internal Markdown-ссылкой.

## 8. Ключевые сценарии

### Сценарий 1. Агент хочет понять исходящие зависимости документа

1. Агент вызывает `get_outgoing_links` для документа.
2. Сервис возвращает список документов, на которые он ссылается.
3. Агент использует результат для impact analysis или навигации по контексту.

### Сценарий 2. Агент хочет понять, кто использует термин или методологический документ

1. Агент вызывает `get_incoming_links` для документа с термином или методологией.
2. Сервис возвращает список документов, где этот документ упоминается ссылкой.
3. Агент понимает blast radius изменения.

### Сценарий 3. Агент перемещает документ

1. Агент вызывает `move_markdown_file` с old path и new path.
2. Сервис находит все incoming links.
3. Сервис физически перемещает файл.
4. Сервис пересчитывает относительные ссылки во всех source files.
5. Сервис обновляет graph index.
6. Агент получает отчет об изменениях.

### Сценарий 4. Агент удаляет документ

1. Агент вызывает `remove_markdown_file`.
2. Сервис показывает входящие ссылки и применяет выбранную стратегию обработки.
3. Сервис удаляет файл и обновляет индекс.
4. Агент получает список затронутых документов и остаточных проблем.

## 9. Architectural drivers

### Correctness over cleverness

Главная ценность инструмента — не просто быстро найти текстовые совпадения, а корректно обновить ссылки. Ошибка в пересчете ссылок может повредить Source of Truth проекта.

### Dry-run как обязательный safety layer

Операции `move` и `remove` должны поддерживать dry-run, чтобы агент мог увидеть planned changes до записи на диск.

### Локальность и безопасность

Сервис должен работать только внутри заданного project root. Любые операции с путями должны защищать от выхода за границы root через `..`, symlinks или абсолютные пути.

### Incremental updates

Для маленького проекта полный re-index может быть достаточным. Но продукт должен проектироваться так, чтобы позже перейти к incremental indexing без смены пользовательского контракта.

### Explainability for agents

Каждая изменяющая операция должна возвращать машинно-читаемый и человеко-читаемый отчет: что было найдено, что изменено, что не удалось изменить безопасно.

## 10. Assumptions

- Основной формат документации — Markdown-файлы на локальной файловой системе.
- Первичный потребитель — ИИ-агент через MCP, а не человек через GUI.
- Большинство важных ссылок между документами оформлены как Markdown-ссылки или близкие к ним форматы.
- На первом этапе достаточно работать в пределах одного project root.
- Для первого MVP допустим полный re-index после изменяющих операций, если производительность остается приемлемой.

## 11. Unknowns и white spots

### Link syntax coverage

Необходимо уточнить, какие виды ссылок поддерживать в MVP:

- стандартные Markdown inline links: `[text](relative/path.md)`;
- reference links: `[text][id]` и `[id]: path.md`;
- Obsidian-style wiki links: `[[note]]`, `[[path/to/note|alias]]`;
- anchors: `file.md#section`;
- links without `.md` extension;
- image links: `![alt](path.png)`;
- external URLs.

Почему важно: от этого зависит parser, модель Link и правила безопасного rewrite.

### Rewrite policy для ссылок с anchors и aliases

Нужно определить, как сохранять `#anchor`, query-like suffixes, aliases и display text при пересчете ссылок.

Почему важно: move должен менять только target path, не ломая семантику ссылки.

### Remove semantics

`remove` потенциально опаснее, чем `move`: удаление ссылки может изменить смысл текста. Требуется выбрать безопасную стратегию по умолчанию.

Предварительная рекомендация: для MVP сделать default `dry-run` или режим `delete_file_only_and_report_broken_links`, а destructive rewrite требовать явной стратегии.

### Graph DB choice

Идея продукта предполагает graph DB, но для MVP нужно проверить, действительно ли нужна отдельная graph database. Возможно, для локального инструмента достаточно SQLite с таблицами files/links или embedded graph representation.

Почему важно: выбор storage влияет на сложность, переносимость, скорость старта и операционную поддержку.

### File watching vs explicit re-index

Необходимо решить, должен ли сервис отслеживать изменения файлов автоматически или индекс обновляется явной командой.

Предварительная рекомендация: для MVP начать с explicit indexing/re-indexing, затем добавить watcher как улучшение.

## 12. MVP definition

MVP можно считать успешным, если сервис:

1. принимает project root;
2. индексирует Markdown-файлы внутри root;
3. строит incoming/outgoing link graph для resolved internal Markdown-ссылок;
4. возвращает входящие и исходящие ссылки для указанного файла;
5. выполняет dry-run для move с отчетом о planned link rewrites;
6. выполняет move с физическим перемещением файла и обновлением incoming links;
7. после move не оставляет битых ссылок на старый путь для поддерживаемых типов ссылок;
8. имеет понятные ошибки для unresolved/unsupported links.

`remove` можно включить в MVP в безопасном минимальном виде: удалить файл только после dry-run отчета и вернуть список входящих ссылок, которые станут broken. Автоматическое удаление упоминаний лучше рассматривать как следующий этап после фиксации rewrite semantics.

## 13. Product principles

- Сервис не должен угадывать опасные изменения молча.
- Любое массовое изменение ссылок должно быть объяснимым и проверяемым.
- Если ссылка не может быть безопасно разобрана или переписана, сервис должен оставить ее без изменений и явно сообщить об этом.
- Project root является жесткой границей безопасности.
- Контракты MCP-инструментов должны быть стабильнее внутренней реализации storage.
- Для агента важен не только результат, но и отчет о blast radius.

## 14. Предварительные success metrics

- Агент может получить incoming links без `grep` по репозиторию.
- Move Markdown-документа выполняется одной MCP-командой с корректным обновлением ссылок.
- Количество ручных исправлений относительных путей после move стремится к нулю для поддерживаемых link types.
- Сервис явно показывает unsupported/unresolved cases вместо silent failure.
- Индексация малого/среднего проекта занимает приемлемое время для интерактивной работы агента.

## 15. Что можно предварительно freeze

- Продуктовая проблема: агентам не хватает структурного знания о входящих ссылках Markdown-документов.
- Основной продуктовый сценарий: incoming/outgoing links, move with link rewrite, remove with impact handling.
- Project root как граница анализа и файловых операций.
- Необходимость dry-run для изменяющих операций.
- Machine-readable отчет как часть каждого mutating tool contract.

## 16. Что требует validation перед архитектурным freeze

1. Поддерживаемый набор Markdown/Obsidian link syntaxes для MVP.
2. Выбор storage: graph DB vs SQLite/index files/in-memory graph.
3. Правила rewrite для anchors, aliases, extensionless links и reference-style links.
4. Безопасная default-стратегия для `remove`.
5. Требования к производительности на реальных проектах workspace.
6. Требуется ли file watcher в MVP или достаточно explicit re-index.

## 17. Следующий рекомендуемый шаг

Следующий шаг — подготовить lightweight product requirements и architecture discovery:

1. Зафиксировать MVP link syntax matrix.
2. Описать MCP tool contracts в виде draft spec.
3. Провести spike experiment на 2–3 реальных project folders: извлечь Markdown-ссылки, построить incoming/outgoing graph и проверить сложность корректного rewrite относительных путей.
4. После spike принять ADR по storage backend и parser strategy.
