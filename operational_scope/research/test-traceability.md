Вот что реально используется в индустрии (и что можно взять как основу для твоего кейса с `requirement → suite → test case → test implementation`).

# 1. Базовый стандарт: **RTM (Requirements Traceability Matrix)**

Это не просто практика — это де-факто стандарт QA.

👉 Суть:

* requirement ↔ test case ↔ execution ↔ defect
* двунаправленная трассировка (forward + backward)

📌 Ключевые правила:

* **у каждого requirement есть уникальный ID**
* **каждый test case ссылается на requirement**
* **все связи живут в одном месте (или синхронизированы)** ([TestRail | The Quality OS for QA Teams][1])

Пример структуры:

```
Requirement ID → Test Case IDs → Test Result → Bug ID
```

👉 Это именно то, что ты хочешь — просто добавь ещё уровень *implementation*.

---

# 2. Стандарты идентификаторов (ID conventions)

### 2.1 Requirement ID

Рекомендуемый формат:

```
FR-AUTH-001
NFR-PERF-002
```

Почему:

* модуль + тип + номер
* легко grep'ается
* устойчив к масштабированию ([TestRail | The Quality OS for QA Teams][1])

---

### 2.2 Test Case ID

Нет строгого ISO-стандарта — но есть best practices:

```
TC-AUTH-LOGIN-001
TC-PAYMENTS-REFUND-NEG-002
```

или проще:

```
TC-000123
```

📌 Требования:

* уникальный ID обязателен ([Qase][2])
* можно включать домен/фичу для читаемости ([Virtuoso QA][3])

---

### 2.3 Test Suite ID

```
TS-AUTH
TS-PAYMENTS
```

# 3. Как связывают test case ↔ код (это уже ближе к твоему вопросу)

Здесь нет строгого стандарта — но есть **устоявшиеся практики**:

## ✅ Вариант A (самый распространённый)

### ID в test case + ссылка в коде

```python
def test_login_success():
    """
    TC-AUTH-LOGIN-001
    Requirement: FR-AUTH-001
    """
```

Почему это хорошо:

* grep-friendly
* легко парсить regex'ом
* не зависит от framework

👉 Это прям best practice:

> “Each test case should reference which requirements it validates” ([TestRail | The Quality OS for QA Teams][1])

---

## ✅ Вариант B (через metadata / annotations)

Например pytest:

```python
import pytest

@pytest.mark.test_id("TC-AUTH-LOGIN-001")
@pytest.mark.requirement("FR-AUTH-001")
def test_login_success():
    pass
```

Плюсы:

* машинно читаемо
* удобно для CI / отчётов

Минус:

* grep хуже работает (но всё ещё ок)

---

## ✅ Вариант C (BDD / Gherkin стиль)

```gherkin
@TC-AUTH-LOGIN-001
@REQ-FR-AUTH-001
Scenario: Successful login
```

# 4. Что важно для парсинга (и ИИ-агентов)

Из практики + рекомендаций:

### 🔑 1. Простая и стабильная грамматика

Не делай свободный текст.

❌ плохо:

```
Test case for login success
```

✅ хорошо:

```
TC-AUTH-LOGIN-001
```

---

### 🔑 2. Регулярное выражение должно быть тривиальным

Пример:

```
TC-[A-Z]+-[A-Z]+-\d+
```

---

### 🔑 3. Один test case = один ID

👉 Это best practice:

* тест должен быть атомарным ([Virtuoso QA][3])

---

### 🔑 4. Не кодируй слишком много смысла в ID

⚠️ важный момент:

* ID должен быть **стабильным**
* название можно менять, ID — нет

# 5. Как обычно выглядит полная цепочка

Реальный production-паттерн:

```
Requirement:
  FR-AUTH-001

Test Suite:
  TS-AUTH

Test Case:
  TC-AUTH-LOGIN-001

Implementation:
  test_login_success()
```

Связи:

```
FR-AUTH-001
   ↓
TC-AUTH-LOGIN-001
   ↓
test_login_success (code)
```

Построение цепочки *Requirement → Suite → Test Case → Test Implementation* — это классическая реализация **Requirements Traceability Matrix (RTM)** (матрицы трассировки требований). В индустрии такие практики регламентируются стандартами качества вроде ISO/IEC/IEEE 29119 для тестирования ПО.

Чтобы идентификаторы было удобно парсить регулярными выражениями (`grep`), скриптами статического анализа и ИИ-агентами, структура должна быть строгой, предсказуемой и легко читаемой машиной.

Вот лучшие практики того, как это организовать:

### 1. Формат уникального идентификатора (Test ID)
Индустриальный стандарт — это мнемонический составной идентификатор без пробелов. Идеально подходит формат, напоминающий тикеты в трекерах:
**Шаблон:** `[Сущность]-[Компонент/Сьют]-[Порядковый номер]`

* **Requirement:** `REQ-AUTH-01`
* **Test Suite:** `TS-AUTH`
* **Test Case:** `TC-AUTH-001`

**Почему так:** ИИ-агенты и LLM отлично воспринимают такие конструкции как единый смысловой токен. Команда `grep -r "TC-AUTH-001"` даст 100% точное попадание, в отличие от поиска по простым номерам вроде `1` или `001`, которые могут встретиться где угодно в коде.

### 2. Организация в `test-map.md`
В Markdown-документации (особенно если вы используете системы управления знаниями на базе обычных текстовых файлов и планируете интегрировать локальные или облачные LLM для помощи с заметками) лучше использовать единообразное форматирование. 

Отлично работают заголовки, таблицы или блоки метаданных:

```markdown
### [TC-AUTH-001] Проверка входа с валидными данными
**Requirement:** [REQ-AUTH-01]
**Suite:** [TS-AUTH]
**Description:** Пользователь должен успешно авторизоваться при вводе корректных данных.
```
Квадратные скобки `[]` или хештеги (например, `#TC-AUTH-001`) служат надежными "якорями" для инструментов поиска (вроде Tavily) и агентов, исключая двусмысленность при чтении файла.

### 3. Интеграция в Python-коде
В коде есть два отличных пути. Первый — в `docstring`, как вы и планировали. Второй — на уровне архитектуры фреймворка, что дает больше контроля.

#### Вариант А: Стандартизированные Docstrings
Используйте формат метаданных Sphinx (reStructuredText) или Google Style. Парсеры документации и ИИ понимают их нативно.

```python
def test_user_login_success():
    """
    Проверяет успешный вход пользователя в систему.

    :test_id: TC-AUTH-001
    :requirement: REQ-AUTH-01
    """
    # реализация теста
```
Для `grep` поиск элементарен: `grep -rn ":test_id: TC-AUTH-001" tests/`.

#### Вариант Б: Pytest-маркеры (Рекомендуемый для интроспекции)
Если вы строите сложные инструменты интроспекции кода и анализируете связи (например, используя AST-парсеры вроде `LibCST` для выстраивания графа вызовов или дерева определений), то хранить ID в декораторе намного эффективнее, чем парсить текст комментариев.

```python
import pytest

@pytest.mark.test_id("TC-AUTH-001")
def test_user_login_success():
    """Проверяет успешный вход пользователя в систему."""
    # реализация теста
```
**Преимущества:**
* Вы можете запускать тесты локально прямо по ID: `pytest -m test_id -k "TC-AUTH-001"`.
* Скрипты могут использовать API Pytest для генерации отчетов (JSON/XML), автоматически извлекая эти маркеры для сопоставления с вашей `test-map.md`.

### 4. Специфичные советы для парсинга ИИ-агентами
Если ваш код и Markdown будут читаться агентами (например, на базе моделей семейства Qwen или Gemini):
* **Используйте дефисы, а не подчеркивания:** Дефисы (`TC-AUTH-001`) предпочтительнее нижних подчеркиваний (`TC_AUTH_001`), так как они лучше ложатся на паттерны токенизаторов моделей при анализе текста и markdown.
* **XML-теги в докстрингах:** Если вам нужна железобетонная гарантия, что ИИ или парсер безошибочно извлечет ID из большого блока текста, оберните его в теги. Модели идеально натренированы извлекать информацию между тегами: 
    `<tc_id>TC-AUTH-001</tc_id>`

Ниже – разбор стандартов, рекомендуемый формат, варианты реализации в Python и советы по удобному парсингу (в том числе для ИИ-агентов).

### 🔍 Что говорят стандарты?
| Стандарт / Гайд | Что требует | Примечание |
|----------------|-------------|------------|
| **ISTQB / IEEE 29119** | Уникальный идентификатор тест-кейса, связь с требованиями, возможность аудита | Не диктует синтаксис, но требует однозначности и прослеживаемости |
| **IEC 62304 (мед. ПО)** | Traceability matrix `REQ → ARCH → TEST → DEFECT` | IDs должны быть стабильны между версиями |
| **ASPICE / DO-178C** | Bidirectional traceability, версионирование связей | Часто используют префиксы `SYS-`, `SWE-`, `TC-` |
| **Agile / DevOps практики** | Легковесные, машинно-читаемые ID, интеграция с CI/CD | Предпочитают плоские или слабоиерархические схемы |

👉 **Вывод:** стандарты требуют **уникальности, стабильности и возможности автоматической выборки**, но оставляют формат на усмотрение команды.

### 🏷️ Рекомендуемый формат идентификатора
```
{PREFIX}-{AREA}-{SEQ}
```
Примеры:
- `TC-AUTH-001` – тест-кейс для модуля авторизации
- `REQ-PAY-042` – требование к платежному модулю
- `SUITE-LOGIN` – тестовый набор (suite)

**Правила хорошего тона:**
- Только `A-Z`, `0-9`, `-` (избегайте пробелов и спецсимволов)
- Фиксированный префикс (`TC-`, `REQ-`, `TS-`)
- SEQ с ведущими нулями (`001`, `002`...) для лексикографической сортировки
- Не меняйте ID после фиксации в `main` (это ломает трассировку в истории)

### 🐍 Как указывать в Python-тестах
Есть два основных подхода. Рекомендую **комбинировать** их:

#### 1. `pytest.mark` (для машинного парсинга и CI)
```python
import pytest

@pytest.mark.test_id("TC-AUTH-001")
def test_login_with_valid_credentials():
    """Проверка входа с корректными данными."""
    ...
```
✅ Плюсы: нативно читается pytest, легко выгружается в JSON/XML, не зависит от форматирования докстрингов.

#### 2. Структурированный docstring (для людей и grep/ИИ)
```python
def test_login_with_valid_credentials():
    """Test ID: TC-AUTH-001
    Requirement: REQ-PAY-042
    Suite: TS-LOGIN
    Проверка входа с корректными данными."""
    ...
```
✅ Плюсы: читается в IDE, отчетах, PR. ИИ и `grep` легко находят по шаблону.

> ⚠️ Не кладите ID в середину произвольного текста. Всегда выносите на отдельную строку с фиксированным тегом.

### 🤖 Парсинг: grep, regex, ИИ-агенты
#### 🔍 Regex для grep / Python / ИИ
```regex
(?i)(?:Test\s*ID|test_id|:test_id:)\s*[:=-]?\s*([A-Z0-9\-_]+)
```
Или для маркеров pytest:
```regex
@pytest\.mark\.test_id\("([A-Z0-9\-_]+)"\)
```

#### 🛠 Пример скрипта на Python для сбора связей
```python
import re
import ast
from pathlib import Path

TEST_ID_RE = re.compile(r'(?i)(?:Test\s*ID|test_id|:test_id:)\s*[:=-]?\s*([A-Z0-9\-_]+)')
MARKER_RE = re.compile(r'@pytest\.mark\.test_id\("([A-Z0-9\-_]+)"\)')

def extract_test_ids(file_path: Path):
    text = file_path.read_text()
    ids = set(TEST_ID_RE.findall(text) + MARKER_RE.findall(text))
    return ids

# usage
for f in Path("tests/").rglob("*.py"):
    print(f, extract_test_ids(f))
```

#### 🤖 Почему это удобно для ИИ-агентов
- Детерминированный шаблон → LLM не гадает, где ID
- Нет вложенной разметки → парсинг через `re` или AST стабилен
- Можно кормить агенту YAML-маппинг + список найденных ID → он строит/проверяет матрицу

### 🗺️ Организация трассировки `REQ → SUITE → TC → IMPL`
Рекомендую хранить связи в **машиночитаемом файле**, а `test-map.md` использовать как человеческую документацию.

#### `traceability.yaml`
```yaml
REQ-PAY-042:
  title: "Пользователь может войти по email и паролю"
  suites:
    TS-LOGIN:
      test_cases:
        TC-AUTH-001:
          impl_file: "tests/test_auth.py"
          function: "test_login_with_valid_credentials"
        TC-AUTH-002:
          impl_file: "tests/test_auth.py"
          function: "test_login_invalid_password"
```

✅ Преимущества:
- Версионируется вместе с кодом
- Легко конвертируется в матрицу (CSV, Markdown, HTML)
- CI может проверять: `все TC из map.md → есть в коде`, `все TC в коде → есть в map.md`

### 🧰 Инструменты, которые стоит рассмотреть
| Инструмент | Что делает |
|------------|------------|
| `pytest-metadata` / `pytest-html` | Добавляет `test_id` в отчеты |
| `Allure` / `ReportPortal` | Нативно поддерживают кастомные ID и трассировку |
| `yq` / `jq` | Парсинг YAML/JSON маппингов в CI |
| `grep -r -P` / `rg` | Быстрый поиск по репозиторию |
| `AST`-парсеры (`libcst`, `ast`) | Точный поиск маркеров/докстрингов без ложных срабатываний |

### ✅ Итоговый чек-лист
1. Используйте формат `TC-{AREA}-{NNN}` (или аналогичный)
2. В коде: `@pytest.mark.test_id("...")` + docstring с `Test ID: ...`
3. Фиксируйте шаблон в `CONTRIBUTING.md` и линтере (pre-commit hook)
4. Храните связи в `traceability.yaml` (или JSON/CSV)
5. В CI добавьте проверку: `все ID из test-map.md → присутствуют в коде`
6. Для ИИ/grep используйте строгие теги, избегайте пробелов в ID
